# Maintenance and extension

Ordinary production happens inside the user's project. Adding or changing the library's own spec, capabilities and default behaviour requires the host's authorisation first; a one-off choice for a single film does not become a long-term rule by itself.

## Adding or deriving a style

First check whether the current catalog can express it through parameters. A stable variant gets a new ID and an external collection:

```sh
python3 scripts/stylepacks.py init brand-ink --into /project/video/styles --extends opuscar-ink-wash
python3 scripts/stylepacks.py resolve brand-ink --style-root /project/video/styles
python3 scripts/stylepacks.py validate --style-root /project/video/styles
python3 scripts/catalog.py --kind style list --style-root /project/video/styles
python3 scripts/validate_plan.py /project/video/plan.json --style-root /project/video/styles
```

`init` only creates a starting point and never overwrites an existing pack. Write down this pack's material, colour, letterforms, motion, camera, sound, native moves, avoidances and fallbacks; verify against the actual brand, Chinese copy, aspect ratio and reading windows. A revision keeps the pack's identity and its callers stable; changing the core medium calls for a new ID.

When a reusable implementation exists, log the actual files, parameters, dependencies and runnable commands, and record where small assets come from. Log key frames, clips, full exports, watching and listening passes by their actual state. Something without a runnable implementation can still be included as guidance — do not fill in placeholder videos or inherit the source's evidence.

## Generating and checking

```sh
python3 scripts/stylepacks.py build
python3 scripts/stylepacks.py build --check
python3 scripts/stylepacks.py validate --sources
python3 scripts/build_gallery.py
python3 scripts/build_gallery.py --check
python3 -m unittest discover -s scripts -p 'test_*.py'
```

`style.json` is the single source of style metadata; `catalog/styles.json` and `styles/README.md` are generated by `build`, and the gallery is then built from the catalog. Never hand-edit generated areas. The built-in catalog always excludes external project and personal collections, so their content cannot leak into the distribution bundle.

The style gallery is `assets/gallery/index.html`, while the motion and recipe catalog stays in `expressions.html`. The former is generated from `styles-template.html`, the latter from `template.html`. Style images are embedded in the HTML, so a copied `index.html` still shows frames, filters and comparisons; playing samples requires the complete directory. The 59 built-in videos live in the corresponding style pack as `sample.mp4`; the gallery uses relative paths and loads them only after an explicit click, and a detail page keeps exactly one player, which stops and releases when the detail closes.

A style pack may carry `gallery.poster` (image inside the pack), `poster_sha256`, `video` (video inside the pack or an HTTPS URL) and `video_sha256`; optionally `attribution.name` / `attribution.url` for a short credit inside the detail view. The legacy `source_url` metadata is still readable, but the gallery never generates an external playback entry. After adding packs and assets, regenerate and they appear in the gallery — no hand-editing of the page list. When an image is missing, the current colour and graphic parameters are used. The gallery does not inherit from the base style, and case assets and the new pack's actual result are accounted for separately. The 59 Lemo-Opuscar styles show only a one-line credit inside the detail view; base styles carry no such label.

The 59 representative frames are imported by `import_gallery.py` from a verified local checkout pinned to a fixed commit; only `styleboard/img/<slug>_0.jpg` is taken, and the already-integrated video bindings are preserved. Samples are imported serially by `import_samples.py` from a reviewed web Release asset manifest: first check size and SHA-256 against the GitHub release, then probe video track, duration and dimensions. The audio tracks of game-show, paper-lantern and news-package are not distributed; when removing a track, verify that the hash of the video payload stays identical. Interrupted and temporary downloads stay in the ignored directory `Output/gallery-downloads`; already verified files may be reused.

The representative-frame list is `assets/gallery/reference-frames.json`; the sample list is `assets/gallery/samples.json`, recording asset version, source-file hash, distributed-file hash, media information and change. After importing, run `stylepacks.py build` and `build_gallery.py`; check integrity with `stylepacks.py validate --sources`. After updating a source pack, re-import the assets, so that a metadata refresh cannot restore external links or drop a local binding.

```sh
python3 scripts/import_gallery.py --source /path/to/inspected-checkout
python3 scripts/import_samples.py --release-manifest /path/to/reviewed-release-assets.json
python3 -m unittest discover -s scripts -p test_gallery.py
```

Interaction-logic checks are isolated tests; they do not replace real browser layout, playback and mobile acceptance. Website operations keep using the Chrome routing the host requires; when a security policy blocks it, keep the unverified scope recorded instead of routing around it with another browser.

## Importing or updating upstream

The current pin is `lemomo-ai/lemo-opuscar` at `413a6bd6d78ebd3bdd5abaec9538a26867f890df`. Study the version delta, licence, compatibility and workflow differences first, then change the importer's pinned version and adaptation rules; ordinary production never pulls `latest` automatically.

`import_opuscar.py` imports from a verified local Git checkout and checks that HEAD and the tracked files are unmodified; it uses `styleboard/catalog.json` from that checkout. It installs nothing, goes online never, and runs no upstream code. A sparse checkout may fetch only the text sources needed; the checkout passed in must contain every file to be included.

```sh
python3 scripts/import_opuscar.py --source /path/to/inspected-checkout
```

An already-present source pack requires an explicit `--replace` after the change has been reviewed. The importer keeps the library's older packs; it writes the upstream's complete STYLE, DEMO, source metadata, usable text sources and CREDITS, while fonts, sound sources, images, video, models and datasets stay in the using project and are prepared under its licence. Even the shared core is only source code — it promises nothing about running the upstream `build.sh` directly. `manifest.json` records a per-file hash and `validate --sources` checks integrity.

Upstream AGENTS files are saved as `AGENTS.upstream.md`, so they are not loaded as this project's agent rules. Third-party source stays as it is; the actual adaptation is written in this pack's STYLE.md and in the project, with the licence kept alongside the pack. After adding upstream code, check for gaps against its declared dependencies, resources and assets.

## Other capabilities

Adding scenarios, motion, expressions and recipes follows the existing data interfaces of the [extension contract](references/extension.md) and the [plan contract](references/plan-contract.md); reuse stable IDs, parameter units, capabilities, conflicts, fallbacks and evidence fields. They combine with styles by semantics — do not add a near-duplicate catalog or force an engine for a single reference effect.

After changing an interface, regress the old plans, external style loading, name collisions, dependency cycles, path boundaries and evidence isolation; choose actual engine and export tests by the risk of the change, and run resource-heavy tasks serially.
